iframe + Live Web vs CEF — Honest Verdict

Question: does the FreeShow web-item pipeline work with the <iframe> syntax already in this app, with minimal changes — and is the current external-browser approach better UX than an embedded window (CEF)? Short answer: yes, and yes — for a worship presenter. Details + receipts below.

Verdict — 95% sure, not 100% (honestly)

Why not 100%: the remaining 5% is OS edge cases (no browser installed, Wayland fullscreen quirks, kiosk lockdown) — all handled by graceful fallback to the offline tile, never a crash. Core path needs ~0 new deps, 0 schema changes: extract_website_embeds → Slide{footer:WebSite} → live_url_for_slide → LiveView::show is already wired and tested. CEF is the better choice only if you need composited web-inside-slide (lyrics over a live page, alpha blending). For everything a church operator actually does, the external hardened browser wins.

01 — What already exists (receipts)

iframe syntax — done

  • vp-core/src/slides.rs:32 extract_website_embeds() — quote-aware, case-insensitive, swallows </iframe>, strips tag from lyrics.
  • Bad URLs (javascript:, spaces, empty) dropped silently, tag still stripped — projection never shows markup.
  • Embeds extracted before chord-stripping (slides.rs:406) so [1] in URLs isn't eaten as a chord.
  • Iframe-only lines leave no blank lyric slide; one link-card slide per unique embed, deduped case-insensitively on scheme+host.
  • 20+ regression tests: iframe_embeds_parse_out_of_lyrics…, byte-safety, quote-awareness, blank-slide, dedup.

Live web view — done

  • app/src/live_web.rs (703 lines) — LiveView spawns a hardened OS browser, kills it on slide-leave and on drop.
  • Chromium: --incognito --app=URL in throwaway 0700 profile, background networking/sync/extensions/translate off. Firefox fallback: private window.
  • Loopback exempt, remote needs per-session Allow + TCP-only reachability check — app never fetches HTTP itself.
  • Fullscreen geometry only on non-primary projector output; windowed on control screen so the operator is never locked out.
  • live_url_for_slide() accepts WebSite/YouTube footers, re-validates via normalize_website_url. Wired in main.rs:3192 sync_live_web + ux.rs:1142 live_web toggle (default off).
02 — FreeShow mapping = minimal diff
1

Add — already done

FreeShow Items.svelte + itemHelpers.ts creates web:{url:""}. Ours: typing <iframe src="…" title="…"> in any lyric line is the "add" — zero palette work, works in songs, not just a special item.

2

Configure — already done

FreeShow boxes.ts exposes web.src + noNavigation. Ours: src= attribute is the URL field, title= is the card label, Background > Website > Live toggle is noNavigation inverted (default tiles-only = navigation off).

3

Dispatch — already done

FreeShow SlideItems.svelte switches item.type==="web". Ours: slides.rs appends Slide::text(header,[url],footer=WebSite) per embed; live_web::live_url_for_slide gates on that footer. Same switch, different spelling.

4

Sanitize — already done

FreeShow checkURL(): unescape, prepend scheme, new URL() validate. Ours: schema.rs:990 normalize_website_url() — identical contract, shared by style backgrounds and embeds. javascript: dies in both.

5

Scale / interact — intentionally different (better)

FreeShow injects body.style.transform:scale() into a <webview> (and skips it for embed URLs because it breaks). Ours skips the problem entirely: the tile stays a tile; the live page opens at native resolution in a real browser with real scroll/keys/video decode. No transform hacks, no mute juggling.

Remaining work (small): per-item "allow navigation" override (~1 checkbox plumbed to live_web_confirmed) + back/forward hover bar (optional; the OS browser already has it) + projector-geometry polish on Wayland. No schema migration. No new crates.
03 — CEF: what it would actually cost here

What "embed CEF" means in Rust + GPUI 0.2.2

  • No GPUI web-view element exists. CEF needs offscreen rendering → shared texture → custom GPUI element, plus hand-rolled focus/keyboard/scroll/IME plumbing.
  • Candidates: cef crate (thin bindings, version-pinned, build-fragile), wry (WebView2/WKWebView/WebKit — not CEF, still needs a GPUI embed shim), or vendoring Chromium (~150–250 MB added to every download, pinned toolchain).
  • Linux reality: X11 vs Wayland Ozone flags, GPU sandbox flags per distro, IME/dialog parenting — the exact class of bugs FreeShow never sees because Electron ships its own Chromium.
  • Security: you inherit Chromium CVE duty + sandbox config. Today the app holds zero browser CVEs because the browser isn't in the binary.

Why FreeShow gets away with embedded

FreeShow is Electron — Chromium is already paid for (download size, memory, sandbox, updates). <webview> is nearly free for them. In Rust/GPUI you'd pay the full price to re-acquire what Electron bundles: a second Chromium beside the user's already-installed one. That's why the external-window design is cheaper here and not a compromise.

05 — Honest review: which is better?

Choose current approach when… (this project)

  • Worship presenter: operator drives, congregation watches. Fullscreen-correct + crash-proof beats composited-pretty.
  • Offline-first is a selling point (church halls with bad wifi, stage servers on loopback).
  • Small team: zero browser CVEs, zero Chromium toolchain, tests stay hermetic.
  • License hygiene: no Chromium redistribution, no codec licensing threads.

Choose CEF when… (not this project, yet)

  • A paying customer demands lyrics-over-live-web compositing or transparent lower-thirds on a stream.
  • Kiosk/locked-down PCs with no allowed browser install.
  • You need pixel-capture of the page into NDI/record pipeline (external window can't be textured).
Recommendation: ship the FreeShow pipeline on top of the existing <iframe> + LiveView path now (minimal diff, better UX than <webview>: native scroll/keys/video, no transform hacks, crash-isolated, operator never locked out). Gate CEF behind a real compositing requirement — spike it only when someone pays for overlays-over-live-page or NDI-capture-of-page. Until then CEF is 200 MB of cost for negative UX.
